## 1. 产品目标与边界

**一句话**：一款模仿早期 Flash 小游戏气质的 2D 横版魔性格斗网页游戏，借助夸张舞步、喊招配音和轻松的人机对战，为未来朋友之间的趣味互动打下基础。

- **[已确认]** 首版不是专业电竞格斗，也不是完整社交平台。优先有趣、易学、能玩完一局。
- **[已确认]** 用户打开网页直接看到游戏场景，没有首页菜单、角色选择、难度选择和注册登录。
- **[已确认]** 首版只做「玩家 vs 电脑」；联网、真人头像、社交分享、竖屏掌机玩法另记 TODO。
- **[已确认]** 产品路线为阶段一单机人机、阶段二异步PvP/离线分身对战、阶段三轻社交成长。后两阶段尚未进入开发，详情集中在 `TODO.md`；不加入本文件的阶段一规则或验收清单，不为未来等级与成长改变当前战斗数值。
- **[已确认]** 技能、数值、动画/皮肤、声音可以分别调整。不能因为改一张图而改伤害计算。
- **[已确认]** 用户体验是轻松、Q版、搞笑；游戏机制保持简单，不追求逐根骨骼的精确命中。

### 1.1 首版成功标准

用户在现代手机横屏或电脑浏览器打开网页，看到一个玩家角色和一个电脑角色；首次有效操作后即开打；能左右走、跳、蹲、格挡、普通攻击、闪身和踢击；有角色动作及对应语音/音效；能扣血、KO或超时结算；不跳转菜单即可重玩。完整闭环比大量内容更重要。

- **功能完成标准**：可以正常打完一局，没有明显操作和规则错误，满足第10节验收清单。
- **体验完成标准**：闪身、踢击、喊招和受击反馈足够有趣，玩家愿意主动再玩一局；通过实际试玩判断，不能用功能测试通过代替。

### 1.2 阶段一不解决的问题

阶段一不设计联网、公会、好友、支付、装备、角色升级、排位、商店、赛季、专业帧表、复杂连招、角色差异化平衡或多场景运营。**UI的具体风格、角色精美程度、动画审美、结算嘲讽文案在当前原型打磨期独立设计**；本文只提出功能约束，视觉设计不改动既有战斗规则。

## 2. 游戏流程：进入即玩

### 2.1 状态流

`加载资源 → 场景就绪/等待首次玩法输入 → 对战中 → 暂停（可恢复） → 结果 → 再来一局`

1. **加载**：加载一套必要场景、人物和技能资源；展示最简单的加载反馈，不能让用户以为卡住。
2. **就绪**：显示双方人物、血条、时间和操作控件。电脑不动，60秒尚未开始。没有额外的“开始游戏”页面。
3. **开战**：用户第一次按移动/技能键或触摸摇杆/技能按钮，就在同一次输入中启动对局，**该次输入本身也必须生效**。第一次网页交互同时尝试解锁音频；音频不可用时照常开战。
4. **对战**：玩家与AI使用同一套基本战斗规则，直到一方HP归零或倒计时结束。
5. **结果**：胜/负/平一目了然；再点一次/按对应键即可重置到新局。具体结算美术和趣味文案后续设计。
6. **中断**：浏览器页面不可见、失去焦点时自动暂停；回来恢复，不补算离开期间的时间。

**[首版默认]** 一局60秒、双方初始100 HP、单回合、不计算三局两胜；同一逻辑步双方伤害统一结算后检查KO，双方同时归零判平局，否则KO立即结束。时间到时比较**剩余HP比例**，相同为平局。所有初始数字位于 `config/balance.json`。

**[已确认]** 不依赖账号及后端API；部署后首次打开仍需获取静态资源，因此“单机”是**无需联网服务器对战**，不是承诺无网络也能首次加载。

## 3. 战斗场地和角色移动

### 3.1 空间与镜头

- **[已确认]** 传统《街霸》式横版格斗，**不存在地面纵深走位**；地面只有 `x` 左右位置，竖直方向表示跳跃高度。
- **[首版默认]** 单个固定擂台，固定镜头，人物不离开可见边界；参考逻辑尺寸960×540，按设备等比缩放，不按不同手机分辨率修改攻击范围。
- **[已确认]** 双方默认面向彼此；穿到对方另一边后自动调整朝向。普攻、浪子踢球和九连环从发动到动作结束锁定攻击朝向，不随对手换边转向追踪；动作结束或被打断后恢复自动面向对手。闪身步可在穿身后自动转身，但不改变本次位移方向。视觉转身可有短动画，但不能影响基本控制。
- **[首版默认]** 普通地面行走不能直接穿身；闪身步可以穿身；跳过对手头顶可以换边。这三项分别配置。改配置只在对应行为已实现的前提下生效。
- **[首版默认]** 跳跃按固定高度和时间完成，允许空中前/后移动；落地时不允许两人长期重叠。不要引入复杂刚体物理引擎。

### 3.2 输入规则

| 输入 | 玩家动作 | 备注 |
|---|---|---|
| 左/右 | 地面前后行走；空中水平控制 | 自动面向对手，不用控制人物朝向 |
| 上 | 原地跳 | 按下触发一次，不因长按不停连跳 |
| 左上/右上 | 向左/右跳 | 不是朝场地纵深斜着走 |
| 下 | 下蹲 | 松开恢复站立（若不在攻击/受击中） |
| 左下/右下 | 下蹲+方向输入 | 远离对手方向可蹲防 |
| 向后按住 | 后退；在攻击判定到来时视为站防 | 不额外设置第五个防御按钮 |
| 普攻键 | 普通攻击 | 可连按，但动作未结束不能无限触发伤害 |
| 闪键 | 闪身步 | 主动躲避，短距离穿身可能换边 |
| 踢键 | 浪子踢球 | 攻击、击退 |
| 必键 | 九连环 | 夸张多段攻击，冷却较长 |

**[已确认]** 手机上的左手是屏幕虚拟摇杆、右手是4个技能按钮；电脑使用键盘。首版**PC建议** `A/D`移动、`W`跳、`S`蹲、`J`普攻、`K`闪身、`L`踢、`U`必杀；方向键可作为移动别名。虚拟按键已有临时布局，正式造型、尺寸、坐标在阶段一UI/交互打磨中结合真机试玩确定。

**[首版默认]** 手机同时按住摇杆与技能按钮必须有效；每个触点保持自己的控制归属；手指滑出或系统中断时必须释放输入，不能卡在一直移动或出招的状态。

### 3.3 同时输入的处理（最小规则）

1. `KO/受击` 优先级最高，其次是已在执行、不可打断的技能动作。
2. **正常状态**下，按下攻击按钮可启动合法技能；移动、跳跃、下蹲输入按当前角色状态处理。
3. 角色正在放招时，不允许另一技能立即覆盖；按键可以无效，**首版不做复杂输入缓冲或取消连招**。
4. **[首版默认]** 空中支持普攻，不允许闪身步、浪子踢球和九连环；将来可加入空中特殊招式。
5. 同一瞬间按多个技能按钮，只接受按键处理顺序中的第一个合法指令；不要叠加发动。

## 4. 战斗与伤害：小游戏级别规则

### 4.1 只使用简单命中框

- 人物有一个大致的身体受击范围；每个攻击技能有沿发动时锁定朝向向前的**简化矩形命中区域**。
- 普攻/踢击在动作中某个简短有效时间段检测命中，**同一次打击对同一目标至多生效一次**。
- 判定距离、高度是否合适即可；不逐个检测手指脚趾，也不依赖人物图片透明像素。
- 空中普攻可以命中合适高度的角色；跳高到一定程度可避开部分地面攻击。第一版只需可理解的高度阈值，不设计复杂空战系统。
- 命中时扣固定HP，按技能规则击退并产生短暂受击硬直；九连环仅最后一段击退。HP不能小于0。
- **[首版默认]** 每个逻辑步先检查双方攻击，基于本步结算前的状态确定命中、格挡或闪避结果，再统一应用伤害、击退与受击。双方已成立的攻击允许同时造成伤害，不因处理顺序被取消；双方同时归零判平局。

### 4.2 防御、闪避、穿身

| 情况 | **[首版默认]** 处理 |
|---|---|
| 普通地面移动相遇 | 不穿过去，简化处理双方占位 |
| 攻击进入命中范围且对方在正常状态 | 扣血+受击反应 |
| 对方处于地面站立、行走或下蹲状态，并按住远离攻击者的方向 | 视为格挡，承受20%伤害，播放“挡住”反馈；不使用独立格挡按钮 |
| 对方成功处于闪身步躲避窗口 | 本次攻击不造成伤害 |
| 闪身步朝对手方向移动 | 有空间时可以闪到身后；闪身者可自动转向对手，正在攻击的一方保持攻击朝向至动作结束 |
| 闪身步向后移动 | 与对手拉开距离；不会反向穿越 |
| 跳跃越过对手 | 落地后换边并自动面向对手 |
| 被打中时再按闪身步 | 本次受击不能立即取消（不做复杂反击取消机制） |

格挡仅对从正面来的攻击生效；角色换边后根据**当前**双方位置判断前后方向。格挡、闪避、命中必须有容易理解的不同反馈，但视觉表现的具体形状留给UI/美术阶段。

- **格挡状态限制**：攻击或闪身步的整个动作期间（含起手、有效期、收招）、受击、KO及空中均不能格挡。正常地面状态按后方向可以继续后退，同时格挡迎面攻击；不另建格挡状态机。
- **闪身步方向与位移**：发动时有水平输入则采用该方向，无水平输入则朝当时对手所在方向；本次闪身结束前位移方向固定。位移在有效阶段完成，起手与收招不产生闪身位移；穿身后的自动转身不改变位移方向，位移仍受场地边界限制。

### 4.3 不把“拼手速”做成无上限点击

- 普攻允许连续点击，动作节奏是自然的限制；没有额外长CD，但一次动作只能产生一次普通攻击伤害。
- 特殊技能可以设置短CD；CD从**技能被成功接受时**开始计算，技能发动失败不消费CD。
- 九连环虽然是多段动作，但并非按一次就无限次结算伤害。首版约定最多3次有效打击，每次命中时分别结算；同一个打击段不能重复扣血。前两段不击退，第三段命中才按配置击退；“最后一段”指动作中的第三段，不是最后一次实际命中。不自动追击，距离或时机不合适仍可落空，不保证打满24点伤害。
- 不设计能量条、耐力条、复杂伤害倍率、属性克制等系统。

## 5. 首版技能清单

> **功能定位已确认**；下表时长、伤害与范围是**[首版默认的测试起点]**，试玩之后允许修改。以 `config/balance.json` 为唯一数值来源，文档不作为运行时第二份配置。

| 技能 | 按钮 | 行为 | 初始建议 | 限制 |
|---|---|---|---|---|
| 普通攻击 `punch` | 拳 | 近身轻击，可反复出拳 | 5伤害、约280ms动作 | 地面和空中均可用；每次最多命中一次 |
| 闪身步 `dodge` | 闪 | 急速横移，可换边，短暂躲避攻击 | 140px位移、800ms冷却 | 首版地面使用，躲避只在动作有效段成立；发动时锁定位移方向 |
| 浪子踢球 `kick` | 踢 | 稍远距离踢击、击退 | 15伤害、650ms冷却 | 首版地面使用，每次最多命中一次 |
| 九连环 `nineRings` | 必 | 夸张连续打击、明显终结感 | 3段×8伤害、5秒冷却 | 首版地面使用，每段最多命中一次，仅最后一段击退 |

首版技能配置只需要：`damage`、`startupMs`、`activeMs`、`recoveryMs`、`cooldownMs`、`range`、`hits`，以及确有必要的特殊字段（例如闪避位移与躲避窗口）。不设置技能等级、成长曲线、连击倍率等概念。

- **有效动作**：起手 → 命中/闪避有效期 → 收招；在不适用的字段中取0，不要求每种技能复杂分支。
- **CD显示**：右侧按钮可有简单冷却反馈；具体效果由UI阶段确定。
- **原始舞步**：动作命名与正式演绎需核对素材来源。技能作用是游戏化创作，不声称民间舞动作本身就是战斗技法。
- **额外招式**：大跨步、二郎担山、猴子摘桃、簸箕步、钟摆步、跳打步等只写入TODO，不做实现。

## 6. 角色、动画与声音的玩法约定

- **[已确认]** 首版双方使用同一种基础角色，靠配色区分；无角色选择，不存在人物属性差异。
- **[已确认]** 动画、皮肤和UI能够独立替换。换头部贴图或更换动画播放器**不改变**血量、伤害、技能CD、攻击范围。
- **[首版默认]** 最小动作集合：站立、走路、跳跃、下蹲、格挡、普攻、闪身步、浪子踢球、九连环、受击、KO。可以先用程序绘制分件人形，再替换成更好的AI辅助素材。
- **[首版默认]** 技能成功发动时播放对应原创喊招；命中、被格挡、躲开时分别发出短音效；音量可调、可静音。音频未解锁或设备无声也不影响出招。
- **[首版默认]** 小幅击退、短暂命中停顿、残影或闪光可用于强调搞笑打击感。基础表现已实现，正式UI、美术、具体配色和音效风格在阶段一原型打磨期完善。
- **[已确认]** 不直接使用无授权的教学视频、教授肖像/原声或第三方音乐。

## 7. 人机对战

电脑对手不使用大语言模型，不需要路径规划。它只根据距离与自身状态做少量决策：

1. 远离时向玩家靠近；过近时偶尔退后。
2. 处于可攻击距离时随机选择普攻或已就绪的特殊技能。
3. 观察到玩家攻击后，经过一定反应延迟，有一定概率保持防御或使用闪身步。
4. 与玩家使用同一个战斗规则，不能无CD出招、受击时反击或预知玩家输入。
5. **[首版默认]** 仅一档正常难度；规则在配置中提供简短决策间隔/反应延迟参数。

电脑目的是让玩家觉得“我打得中，也有时会被反击”，不是极限挑战或无懈可击的对手。

## 8. 胜负、中断与边界情形

- 同一逻辑步双方伤害统一结算后检查HP；双方同时归零判平局，否则单方归零判负。KO后立即停止继续接受战斗输入；播放KO反馈后显示结果，不允许后续继续扣血。
- 时间到双方都存活时按剩余HP比例比较；相等判平局。首版不做加时赛。
- 重赛完整重置血量、位置、状态、冷却、AI决策和倒计时；不重新访问网页。
- 页面隐藏/应用切后台时暂停计算与音频；恢复后继续正常计算，不一次性追赶离开时长。
- 用户关闭静音、屏幕旋转、设备不支持振动、声音播放失败，不得卡住对战。
- 如果游戏尚未开始，电脑不会偷打、倒计时不会消耗。
- 竖屏打开时显示转横屏提示；不自动强制旋转屏幕，不把竖屏模式开发为首版游戏。

## 9. 设备与可用性要求

- **[已确认]** PC实体键盘及手机横屏虚拟摇杆/四按钮两条输入路径，规则完全相同。
- **[首版默认]** 逻辑场景等比适配，按钮留出刘海、手势条等安全区域；不得把攻击判定绑定到物理设备像素。
- **[待验证]** 至少在一款真实iPhone及一款真实Android手机、PC Chrome与Safari/Firefox目标浏览器验证输入、声音、性能。微信内置浏览器作为扩展测试对象；不承诺所有旧机型100%一致。
- **[已确认]** 不兼容IE11；网页不依赖账号、后端、联网房间、原生App容器。

## 11. MVP执行次序（按可玩闭环，而不是按模块堆功能）

- **M0 技术验证**：两位程序绘制的占位人物，键盘/触控、简单动画、声音、横屏适配在目标浏览器可用。
- **M1 能动**：人物左右走、跳、蹲、朝向、边界；AI能接近。
- **M2 能打**：普攻、闪身步、踢击、格挡、血量、命中、简单受击。
- **M3 完整一局**：九连环、AI反击、倒计时、KO、结果、重赛、背景暂停。
- **M4 有辨识度**：替换成可用的原创Q版角色动画与喊招声音，调整手感，完成关键浏览器测试。

当前已用程序占位素材实现M1–M3的功能框架，并具备M0的本地运行与输入验证；目标真机验证尚未完成。现重点推进M4及正式UI、人物与场景美术、配音、打击反馈和实际试玩，后续完成Web正式部署。以上里程碑保留为实施与验收依据，不因原型已实现就认定全部通过。功能完成以第10节验收结果为准，体验完成以第1.1节的实际试玩结果为准。

## 12. 仍待试玩调参的内容（原型打磨期）

- 具体攻击伤害、动作持续时间、移动速度、攻击距离、跳跃高度、CD。
- 格挡削减伤害的比例，闪身步躲避窗口、位移距离。
- AI反应概率、单局60秒是否恰当。
- 角色动作和声音的实际好笑程度、玩家是否愿意马上重赛。

**约束**：需要调整数值时先改配置并试玩；需要改变机制时先确认是否真正提升趣味性。不要为了“完整格斗系统”制造额外状态与数值。

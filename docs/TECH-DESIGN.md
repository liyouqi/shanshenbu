- **版本**：V1.2（进度与复用原则同步，第一阶段工程基线不变）
- **日期**：2026-11-08
- **权威来源**：玩法要求见 `GDD.md`；此文件只描述怎样实现。后续功能见 `TODO.md`。
- **设计取向**：一个独立开发者 + AI 辅助能够完成；小而清晰，不做专业电竞引擎。

> 标签：**[已确认]** 为用户确认的工程基线；**[首版方案]** 为现在推荐的实现；**[待验证]** 为必须使用实际环境验证的能力；**[后续]** 不进入本次交付。

## 2. 模块与依赖方向

```text
KeyboardInput ----┐
TouchInput -------+--> InputMapper ----> GameLoop/Controller
AIController -----┘                          |
                                            v
                                   CombatCore (纯 TypeScript)
                                    state + simple events
                                      /       |       \
                                     v        v        v
                               CharacterView AudioFeedback HUD/Effects
                                (Phaser)    (Phaser)    (Phaser)
                                           |
                                  optional HapticFeedback
```

这是**代码逻辑的依赖方向**，不代表引入消息队列、插件管理器或事件中台。可以在一个更新循环中简单调用几个普通TypeScript模块。

- **`core/`**：战斗状态与规则（坐标、行动阶段、HP、冷却、命中、格挡、KO）；**不得 import `phaser`**。
- **`skills/`**：从JSON读取技能配置，核心按照相同规则执行4种首版技能；仅对闪身步、九连环存在少量专门分支。
- **`ai/`**：根据战斗状态返回与玩家相同的命令，不得自行修改HP、CD或角色坐标。
- **`input/`**：键盘与触控转换为同样的游戏输入；仅此处知道按键与触点。
- **`game/`**：单一游戏循环、首局启动、暂停/恢复、结束/重赛，协调核心与表现。
- **`view/`**：Phaser场景、角色显示、简单动画、血条、按钮、命中特效。
- **`audio/`**：从核心事件触发原创语音/SFX/BGM；音频不决定战斗结果。
- **`platform/`**：仅实现需要的浏览器能力检测（例如振动可用性）；后续分享可沿这个边界接入。

**换动画、换皮肤、换UI**不得直接修改 `core/` 中的伤害/冷却/命中计算。反过来，核心不能操作Sprite、播放声音或读DOM节点。

### 2.1 后续阶段的架构延续原则（尚未进入开发）

阶段二的异步PvP与阶段三的轻社交成长应尽量复用现有Combat Core、AI Controller、技能配置和动画表现。战斗逻辑不依赖对手来自本地预设还是云端角色快照；快照来源不应改变核心的规则职责，离线对手仍由AI生成合法行动命令。

未来异步PvP的方向是普通HTTP API、云函数和数据库：获取角色快照后在挑战者本地运行战斗，结束后提交结果并记录挑战；被挑战者无需在线，不需要实时WebSocket格斗同步。这只是延续方向，尚未确定完整数据结构或API。

阶段一保持纯前端Web单机。当前不提前开发玩家模型、服务端接口、数据库、网络同步、排行榜或反作弊系统，不为未来接入增加抽象层或重构架构，也不调整现有战斗数值。完整产品范围与待定事项见 `TODO.md`。

## 3. 最小数据与接口约定

只用少量必要字段；不要建大型通用ECS或可插拔插件框架。

### 3.1 输入

```ts
// 每次逻辑更新得到当前输入快照；只代表动作意图。
type FighterInput = {
  horizontal: -1 | 0 | 1;
  up: boolean;       // 单次触发跳跃的按下边沿
  down: boolean;     // 持续按下为蹲
  punch: boolean;    // 单次按下边沿
  dodge: boolean;
  kick: boolean;
  special: boolean;
};
```

- 键盘与触控使用同一个映射结果；AI也生成此结构。
- 连续按住技能键不应每个逻辑tick都新发动一次；移动和下蹲可持续。
- 当两个技能键同时按下时，控制器按简单确定性顺序取第一个合法动作，不叠加。
- `up`+`horizontal` 为方向跳跃；`down`+向后为蹲防。后方向根据实时对手位置判断。

### 3.2 角色战斗状态（建议最简）

```ts
type FighterState = {
  x: number;
  jumpProgress: number | null; // null=在地面；0..1=跳跃过程
  facing: -1 | 1;
  hp: number;
  action: 'idle' | 'walk' | 'crouch' | 'jump' | 'acting' | 'hit' | 'ko';
  actionElapsedMs: number;
  cooldownUntil: Record<string, number>;
};
```

这是接口方向示意，不要求代码照字面逐字段复制；可把 `guard` 视为按键+处于可防状态的派生条件，而不是另建复杂格挡状态机。

- 普通行走互相阻挡；按配置允许特定技能穿身。人物角色位置是游戏逻辑坐标，不取Sprite像素位置。
- `jumpProgress` 允许用简单抛物线计算跳高：`height = 4 * maxHeight * t * (1-t)`，不必引入重力和刚体碰撞求解器。
- 角色跳过对手后自动朝向对手；如果落地交叠，安全挪开，不允许卡死。普攻、浪子踢球和九连环在发动时锁定本次攻击朝向，起手、有效期及收招均不随对手换边转向；**动作结束或被打断后恢复自动转向**。命中判定和攻击动画使用同一锁定朝向，不能中途反手命中。
- 闪身步单独保存发动时的位移方向：有水平输入时采用输入方向，否则朝当时对手所在方向。该方向直到本次闪身结束都不改变；穿身后的显示朝向可自动转向对手，不参与重新计算本次位移方向。
- 规则只保存当前动作、经过时间、可释放时间等极少量信息；不做几十个互斥动画状态。

### 3.3 核心事件

```ts
type CombatEvent =
  | { type: 'action-start'; fighter: 'player' | 'cpu'; action: string }
  | { type: 'hit'; attacker: 'player' | 'cpu'; damage: number }
  | { type: 'blocked'; defender: 'player' | 'cpu' }
  | { type: 'evaded'; defender: 'player' | 'cpu' }
  | { type: 'round-end'; winner: 'player' | 'cpu' | 'draw' };
```

每次 `core.step()` 可以返回简单 `events[]`。`view`、`audio`、`HUD` 分别读取这些事件；**没有必要建设全局EventBus或业务消息中间件**。例如“踢中”事件同时触发受击动画、SFX和轻微击退显示。

## 4. 战斗循环与判定

### 4.1 时间模型

- **[首版方案]** 固定60Hz逻辑步（约16.67ms），显示刷新率可以不同。技能时间字段用`ms`配置，核心根据累积逻辑时间判断动作阶段。
- 限制单帧最大补跑步数；如果页面暂停或帧率骤降，**不能一次追赶几十秒**。后台自动暂停时清理累积时间。
- 显示层保存相邻逻辑步的位置与跳跃高度，用累积器余量插值显示；核心仍固定60Hz，插值不参与命中、伤害或CD。暂停恢复和重赛时重置显示采样，避免画面回跳。
- HUD仅在显示值改变时更新；固定背景预绘制为纹理，减少每帧重复工作。
- 不追求联网级完全确定性与回放同步；当前目的是不同设备上的动作节奏合理一致。

### 4.2 每个更新周期

1. 读取用户输入快照；AI生成电脑输入。
2. 检查当前是否在等待首次有效输入、暂停或对局结束。
3. 处理合法的移动、跳跃、下蹲或技能开始，检查动作锁和CD。
4. 推进动作时间、处理简化穿身/边界/跳跃高度。
5. 基于本步结算前的同一状态，先检测双方有效攻击与对方简单身体框；各次判定在格挡、闪避、命中中只选一个结论，暂不修改HP、击退位置或受击状态。
6. 统一应用双方已成立的伤害、击退与受击或格挡/躲避结果；每个独立打击段对同一目标只结算一次。不能因先处理一方受击而取消另一方本步已经成立的攻击。
7. 双方结果应用完成后检查KO：同时归零判平局，单方归零判负；否则按计时规则结算。返回状态及事件，由表现层渲染与播放反馈。

只需在当前逻辑步用局部变量暂存双方判定结果，无需引入战斗事件队列。受击会中断后续攻击，但不追溯取消同一步已成立的命中。

**不要使用图片是否重叠来判断是否命中**。不要求跟随手脚的复杂骨骼Hitbox。默认用**双方中心点的水平距离、发动时锁定的攻击朝向以及一个简单高度阈值**判断是否命中（`range` 表示允许的最大中心距离；空中与地面错层时可跳过命中）；这相当于足够粗略的矩形有效区，不需要另建复杂图形系统。普通攻击单个范围、踢击一个较长范围；九连环使用3个简单的打击时机。闪身步的无敌窗口和水平位移由核心的计时与配置决定。

### 4.3 格挡、穿身和空中

- 默认角色正常走路互相阻挡；闪身步穿过对手、跳跃越过对手由 `rules` 开关控制。
- 对手从正面击中、且该角色处于地面的站立、行走或下蹲状态并**向后按住**，则按配置减伤。攻击和闪身步的整个动作期间（含起手、有效期、收招）、受击、KO及空中均不能格挡；用当前状态派生可防条件，不另建格挡状态机。初版HP使用整数，格挡伤害可以简单计算为 `Math.round(damage * guardChipRatio)`。
- 持续按后方向不妨碍玩家在无攻击时退后，不另设专用格挡按钮。
- 闪身步只有短暂有效躲避段免伤；CD和攻击动作锁仍须生效。
- 闪身步在 `activeMs` 阶段沿发动时锁定的方向完成 `travelDistance` 位移，起手和收招不产生闪身位移，场地边界可截断位移。躲避窗口从有效阶段开始，持续 `invulnerableMs`，不超过有效阶段；转身不改变位移方向。
- 首版空中只允许普攻，不制作额外空中技能系统。

### 4.4 动作时间来源

`startupMs`、`activeMs`、`recoveryMs` 定义技能总时间；**核心时间为准**，动画按该时间播放或缩放。动画可以更漂亮、帧数可以更高，但不允许改变实际伤害窗口。多段技能使用 `hits` 个均分的独立攻击窗口即可，不需要为每帧单独配置。

九连环的非末段击退为0，仅动作的最后一段命中时使用 `skills.nineRings.knockback`；“最后一段”按打击段序号判断，不按实际命中次数判断。现有配置为3段，因此前两段不击退、第三段击退。不增加自动追击，仍逐段检查范围、朝向与防御/闪避条件，允许落空。

## 5. 配置数据：一个文件就够

唯一首版平衡参数源：**`config/balance.json`**。无需后台、数据库、CSV导入或复杂Schema服务。

- 通过Vite/TypeScript从根目录 `config/balance.json` **静态导入**并做简单校验（非负时长、合理边界、有效数值）。开发时修改并刷新即可观察效果；正式发布后修改该文件需要**重新构建部署**。不增加运行时配置接口。格式错误应显示清楚的开发错误信息，而不是静默乱跑。
- 改动数值保存后刷新即可验证。上线采用打包时的配置，不要求用户在网页内直接编辑数值。
- 配置项包括：HP/局长、场地边界、行走/跳跃、穿身开关、格挡减伤、4个技能的伤害/时长/距离/CD，以及AI最少量参数。
- `knockback` 表示命中时的击退距离；普攻和踢击在各自命中时使用，九连环仅在最后一段命中时使用。沿用现有字段和数值，无需新增逐段配置表。
- **规则开关必须有代码实现**。不能因为配置里写了`walkThrough=true`就声称引擎已支持未实现的行为。
- 不采用复杂公式：固定伤害，必要的格挡倍率，不叠加暴击、成长、属性克制、护甲等。

## 6. 动画与角色美术：独立开发者可落地路线

### 6.1 首选：代码驱动分件动画（混合表现）

首版用Phaser的 `Container`、`Graphics`/`Image` 和简单Tween控制一名原创Q版人物：头、躯干、左右手臂、左右腿。原型可以全部用形状和纯色，**不用先学Blender或亲手画几十帧**。

- 日常动作（站立/走路/跳/蹲）：几个关键姿势，由程序插值。
- 标志性招式（闪身步/浪子踢球/九连环）：明显的蓄势、突然移动/踢击、急停；可以叠加少量残影、运动线、闪光等，而不是大量绘制。
- AI可帮助产出原创角色参考图、分件资源、动作姿势与动画代码，但生成的单帧图片可能前后不一致；**不要把每一帧都独立交给AI重画**。
- 以后如果要使用Sprite Sheet或专业骨骼动画，只替换显示实现；**现在不引入Spine、Rive、Blender作为强依赖**。

### 6.2 动画资源与逻辑的最低约定

- 统一动作标识：`idle, walk, jump, crouch, guard, punch, dodge, kick, nineRings, hit, ko`。
- **脚底为角色画面锚点**：不因为不同大小的图而在地面跳动。角色显示由战斗坐标与跳跃高度决定。
- 左右朝向由核心提供；优先镜像同套动作，确有需要再做不同侧素材。
- **动作时长由核心定义**；显示层负责把相应动画映射到它，不是让音频或动画帧驱动扣血。
- **皮肤与动作独立**：未来头像替换可放置独立头部部件/挂点，但首版不做上传、换脸或账号。

可采用极小接口（只实现一个版本，**不要提前写所有适配器**）：

```ts
interface CharacterView {
  setPose(x: number, jumpHeight: number, facing: -1 | 1): void;
  play(action: string): void;
  setAppearance(appearanceId: string): void;
}
```

首版实现 `PartsCharacterView`。未来如有必要，可在不动核心规则的情况下新增 `SpriteCharacterView`，而不需要把所有动画格式设计成插件系统。

### 6.3 实际动画制作流程

1. **程序占位**：用几个圆形/矩形完成站立、走、跳、闪、踢，首先确认操作和节奏。
2. **动作验证**：只重点做闪身步与浪子踢球，看它是否有笑点、动作是否清楚、音画是否对上。
3. **AI辅助素材**：生成一名固定比例的原创Q版人物、颜色与分件，筛选并修正部件连接位置。
4. **替换素材**：保持骨架/部件层级和脚底锚点不变，把程序形状换成图片；检查转身、遮挡、落地。
5. **只在失败时升级工具**：如果代码驱动的动作明显僵硬，再比较Sprite Sheet导出、AI辅助Rig或Spine；该选择不阻碍MVP。

**验收底线**：同一招换动画/配色后，攻击范围、CD、扣血和AI行为不变。特别复杂的动作需要审美微调，但不应改变核心战斗逻辑。

## 7. 声音、效果与设备能力

### 7.1 音频

- **[待验证]** Phaser Sound Manager在支持的浏览器中优先使用Web Audio，不支持时可使用HTML5 Audio；不承诺各平台延迟一致。
- 把资源分成 `voice`（招式喊话）、`sfx`（破空、命中、格挡、落地）、`bgm`（背景音乐）、`ui`（必要按键与结算音）。**资源分类≠引入四个大型音频子系统**。
- 音频只能在浏览器允许后播放：首次游戏输入尝试解锁；`sound.locked` / unlock事件用于正确处理。解锁失败不影响游戏。
- 技能被合法接受才播放喊招；命中时才播放命中音；语音限制重叠，避免连点叠出十句口号。
- 静音和基础音量选项（可使用浏览器本地存储保存），背景切换自动暂停或衰减。
- 原创声音/获得使用授权的素材，**不直接截取教授原声或他人背景音乐**。

原型当前使用本地生成的短音效，由Phaser播放；喊招使用设备中文语音合成，有可用中文声音才尝试播放，无可用声音或播放失败时保留屏幕喊招文字。该方式用于验证动作节奏，不等同于正式原创录制配音，也不承诺各设备声音一致。

### 7.2 打击反馈

先用低成本而明显的效果：受击者短暂停顿或夸张后仰、轻微击退、闪光、残影、小屏幕震动。应有“命中”“挡住”“躲开”三种可辨识的效果。**表现层的镜头抖动和停顿不要让核心计时失控**。如果需要真正暂停逻辑几帧，也必须由核心统一处理并保持一致。

### 7.3 可选触觉反馈

在支持Vibration API等能力的环境按命中事件短振动；功能检测失败直接跳过。iOS Safari网页不能依赖标准Vibration API。无需首版集成原生插件。

## 8. 浏览器、屏幕、性能

### 8.1 支持目标

- 主目标：Windows Chrome/Edge、macOS Safari/Chrome、iPhone Safari、Android Chrome。
- 验证目标：Firefox、Android Samsung Internet、微信内置浏览器。
- 不支持IE11，不承诺所有旧手机和所有WebView零差异；若微信内置浏览器存在关键限制，公开测试可先引导在系统浏览器打开。
- **微信中打开H5链接**与**微信原生小游戏**是不同平台；首版仅H5，原生小游戏移植列入TODO。

### 8.2 渲染与横屏

- Phaser 4.2.1以**WebGL为主要渲染目标**。其Canvas渲染器仍存在，但官方已提示部分新特效不支持，不能把“Canvas回退时完全一致”当作兼容承诺。
- **[首版方案]** 逻辑舞台960×540，用Phaser Scale `FIT` 等比缩放；按设备布局显示战斗区域、虚拟按钮和安全边距，避免拉伸人物与改变命中尺度。
- 首版只做横屏；若手机处于竖屏，展示转横屏指引，不依赖浏览器强制锁定方向。未来可以在上半部保持16:9画面、下半部放虚拟控制器的掌机式模式。
- 画面特效少且轻；目标现代手机流畅、输入响应明确。60fps为期望而非所有设备保证，低端设备可接受低于60fps；逻辑时间仍按固定步长推进。

### 8.3 触控安全

- 左右两区域多指并行，维护摇杆与各技能按钮的pointer ID；松开、滑出、页面失焦与触点取消必须释放。
- 阻止游戏区域被浏览器滚动、双击缩放或长按选中文字；不要禁止整个页面的必要可访问性行为。
- iPhone安全区域、安卓系统导航栏、横屏工具栏要真机测试。

### 8.4 暂停/恢复

页面隐藏或浏览器失去焦点时暂停计时、逻辑更新和需要暂停的BGM；恢复后重置逻辑累积器，不模拟用户离开期间的所有帧。页面失焦时同时释放全部输入，防止继续跑动。

## 11. 少量必要的自动化测试

- 技能不在范围内不扣血；在范围内一次打击不重复扣血。
- 仅正常地面状态按后可格挡减伤，攻击/闪身的起手、有效期、收招及受击、KO、空中不能格挡；闪避有效时免伤，有效时间外可以被打中。
- 已在技能动作中不能同时开始另一招；冷却期间不重复释放。
- 闪身步有输入按输入方向、无输入朝对手，在有效阶段位移；穿身转向不改变本次位移方向，移动不能越出边界。
- 普攻、踢击、九连环锁定整个动作的攻击朝向，换边不追踪；动作结束或被打断后恢复自动转向。
- 跳越后按当前动作规则处理朝向，落地无持续重叠或卡死。
- 九连环每段至多结算一次；非末段不击退，仅最后一段命中时按配置击退，落空不补伤害或击退。
- 同一步双方已成立的伤害统一结算，同时KO判平局；受击与KO后不产生后续攻击伤害，重赛状态完全复位。
- `balance.json`被改动后加载对应数值；无效配置能明确报错。

其余操作手感、笑点与音画同步以真实设备试玩为主，不要求搭建庞大自动化测试框架。
